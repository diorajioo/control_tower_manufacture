Section 4 — Analyze the Root Cause
Why Did the Gaps Exist?
Tableau was selected as a fast visualization solution — not designed for operational monitoring. The following root causes explain why each gap persisted.
Problem 1 · Passive monitoring
Tableau is a read tool, not an event-driven system
Tableau has no built-in scheduler or webhook mechanism to check KPI values autonomously. It serves dashboards when opened — it does not watch data and push when something changes.
Effect
Problem response time = time between manual checks. Issues can go unnoticed for hours.
Why not Tableau?
Tableau Alerts are limited to specific chart types, cannot be per-user per-KPI, and require admin access.
Problem 2 · Insight takes days
Tableau renders data — it does not reason about it
Tableau's core function is rendering pre-defined visualizations. It has no language model, no summarization engine, and no conversational interface. Adding AI requires external tools with no native data binding.
Effect
Managers spend time reading multiple charts to form a picture that AI could narrate in 3 sentences.
Why not Tableau?
Tableau Pulse (AI) is a separate paid add-on with limited customization, not available in all regions.
Problem 5 · Locked platform (change)
A SaaS platform cannot be extended beyond its API
Tableau Cloud is a closed platform. Custom features — per-user alert logic, Teams integration, AI chatbot, action tracking — are impossible to build inside Tableau. These require owning the application layer.
Effect
Every time a new operational need arises (e.g. "notify quality manager on RFT drop"), it cannot be built.
Why not Tableau?
Tableau does not expose an application development framework. Custom logic must live outside the tool.
Problem 5 · Locked platform (cost)
Per-seat licensing is structurally misaligned with operations
A manufacturing operation needs KPI access for Plant Managers, Shift Supervisors, Quality Teams, and Operations staff. Tableau's model charges per seat regardless of usage frequency.
Effect
Access is rationed to limit cost — roles that would benefit from visibility are excluded.
Why not Tableau?
Fundamental pricing model issue. No free viewer tier or flat-rate enterprise option for small teams.

Section 5 — Improvement Project
PO Lead Time Risk Score
An early-warning score (0–100) for every running PO that combines stage progress, waiting time, product history and queue load into one indicator — weighted by logistic regression on historical POs, explained by AI and pushed to Teams before the PO passes the 13-day target.
Why
Tableau only shows a PO as late after it is late — no room to act.
The 13-day target runs from PO Released → NDC. Measured that way, 19.5% of 2026 POs still miss it.
Signals already exist in Snowflake: every activity of every PO is time-stamped.
4 components · each scored 0–100
Stage Progress
How far the PO has moved through its process steps vs. POs at the same day after release
Waiting
Hours spent in WIP / queues since release vs. the usual amount at that point
Product History
Historical late rate of the SKU group × dosage form (smoothed for small groups)
Queue Load
Number of other open POs in the same plant on that day
What users get
At-risk PO list
Running POs ranked by risk, filtered by plant and stage
AI explanation per PO
Names the component that drives the risk, in plain words
Preventive Teams alert
When a PO crosses the High threshold — reuses the live alert pipeline
Not possible in Tableau: it needs per-PO snapshots, a trained model, AI narration and push alerts — all of which live in the owned application layer.
Section 5 — Improvement Project · Method
How the Risk Score Is Calculated
STEP 1 · SNAPSHOT
Each historical PO is "photographed" on day 2, 4, 6 and 8 after release, using only what was known at that moment.
STEP 2 · SCORE 0–100
Each component becomes a percentile vs. all past POs on the same day. 100 = worst.
STEP 3 · WEIGH
Logistic regression learns how much each component predicts "Released → NDC > 13 days".
STEP 4 · PROBABILITY
Weighted points → chance of being late (0–100%) = the Risk Score. ≥ 70 = High.

THE FORMULA
P(late | PO state) = σ( z )
z = Σᵢ  wᵢ · percentiled( xᵢ )

Finding along the way
Measured from PO Released (the basis of the 13-day target), September lead time is 7.97 days and 13.5% of POs exceed 13 days. Measured from PO Created it is 16.95 days and 53.4% — the extra 8.98 days is Created → Released, an administration phase outside manufacturing.
Limits & next step
Offline backtest — in-app list, AI narration and Teams alert are next. PO Released timestamp is a working hypothesis pending confirmation. POs still open at the data cut are excluded. Late rate fell from 24% to 13% between periods, so mid-range probabilities run high → recalibrate monthly.

Section 7 — Challenges
What Was Difficult to Build
Technical
Snowflake Warehouse Auto-Suspend
Problem
Snowflake warehouses auto-suspend after inactivity. When the dashboard first loads, the warehouse may be suspended — causing a 30–60 second wait before the first query responds. This looked like the app was broken.
Resolution
Implemented a 60-second timeout with a user-facing skeleton loading state. The KPI fetch waits gracefully and shows an animated placeholder while the warehouse wakes up.
⚠ This is a known UX friction point — first load after inactivity is noticeably slow.
AI Integration
Groq API Model Availability
Problem
Several Groq models are restricted or banned on specific API accounts. The application initially used a model that returned 403 errors silently, causing the AI summary to fail without clear error messages.
Resolution
Moved to DeepSeek as the primary model, with one reliable Groq model (qwen3.6-27b) as fallback. If the first call fails, the next model is tried automatically.
⚠ The Groq fallback must be checked when Groq changes model availability.
Authentication
Microsoft Teams Graph API Permissions
Problem
Sending Teams DMs via Graph API requires specific OAuth scopes and a delegated token tied to the logged-in user. Setting up the correct permission chain without requiring tenant-level admin consent required significant trial and error.
Resolution
Used delegated permissions (Chat.Create + ChatMessage.Send) that work with standard user consent. Implemented token refresh alongside NextAuth.js JWT rotation to keep Teams access active.
⚠ Token expiry edge cases still possible on very long sessions without activity.
Data Integration
Wiring Lead Time to Live Data
Problem
The Lead Time page started as static mock data. The source has no due-date column and only 3 stages (TIMBANG, OLAH, CUCI OLAH) have usable standard times, so "on-time" and "vs standard" had to be defined from what the data really holds.
Status
Done for the Strategic view: KPI cards (VA / NNVA / Waste / Potential Saving), weekly trend per stage, SKU scatter, stage Pareto and Top 10 SKU all run on Snowflake. On-time = gross lead time ≤ 13 days. Overview Tactical adds stage vs standard and a per-plant breakdown.
✓ Lead Time now runs on real Snowflake data.
